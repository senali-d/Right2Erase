# ShopKart — demo fixture

A fake online store for the erasure agent to work on. Four systems, all real
services, all yours to connect:

| System | What it holds | How the agent reaches it |
|---|---|---|
| Postgres | accounts, orders, items, refunds, tickets, uploads index, event log | Postgres MCP server |
| MinIO | uploaded objects (avatars, receipts) | S3 MCP server |
| billing-api | customer records, saved cards, charge history | `billing-api/mcp-server.js` (yours) |
| event_log | request lines carrying email + IP | same Postgres connection, no FK |

Every customer is generated by Faker. No real personal data is in this repo,
which is what makes it safe to put on camera.

## Run it

```bash
npm install
npm run up      # postgres + minio + billing-api, waits for health
npm run seed    # ~200 accounts and the five hard cases
```

`npm run reset` tears everything down and rebuilds from scratch — run it
between demo takes so the numbers are identical each time.

Seeding is deterministic (`SEED = 4217`). Same command, same database, same
row counts on your machine and on a judge's.

## The subject

`ravi.sharma@example.com` — 12 orders, 3 support tickets, 2 objects, a saved
card, and 400 log lines. Invented, like everyone else in here.

## The five planted cases

The interesting part isn't the volume, it's the traps. Each one is a beat in
the demo video where the agent has to show judgement rather than pattern
matching.

**1 · Foreign-key ordering.** `order_items` and `refunds` hang off `orders`,
which hangs off `accounts`. Delete top-down and Postgres raises a constraint
violation. The agent has to derive leaf-to-root order for itself.

**2 · Retention hold.** One order carries an unsettled refund — money still
owed. Destroying it would erase the record of a live financial obligation, so
it must be withheld and escalated, not deleted. A *settled* refund also exists
on another order and is safe to remove. Deleting both, or neither, is wrong.

**3 · Name collision.** `r.sharma@example.net` is a different person with the
same display name, 5 orders of their own, and 60 log lines. If discovery
matches on name anywhere, this stranger's data gets destroyed. `npm run truth`
fails loudly if the plan touches them.

**4 · Orphaned object.** A return receipt sits in MinIO with `account_id NULL`
in the uploads table. The only link back to the subject is the account id
inside the object key path, so a join finds nothing and a real search is
required.

**5 · Identity chain.** The subject changed address in September 2024. 180 log
rows are still filed under `ravi.s@oldmail.example`. Discovery has to walk
`account_emails` and search every historical address, not just the current one.

## Verifying without cheating

`scripts/truth.js` computes the correct answer independently, straight from
the database. Keep it out of the agent's MCP surface — it exists so you can
prove discovery actually discovered something.

```bash
npm run truth                          # print the expected manifest
npm run truth -- --diff plan.json      # compare the agent's plan against it
```

The diff prints a row per bucket and exits non-zero on any mismatch, so it
drops straight into CI:

```
  ✓ orders                       12      12
  ✓ order_items                  23      23
  ✗ event_log                   400     220     ← missed the old-address rows
  ✓ withheld records              1       1
```

That last line is the one to keep an eye on. An agent that finds 220 events
looks like it worked, right up until you notice it skipped case 5.

## Reset between takes

```bash
npm run reset && npm run truth
```

Thirty seconds. Do it before every recording.

## What is deliberately absent

No fixture data is loaded into the agent's context, no row counts live in any
config file, and nothing about the five cases is described anywhere the agent
can read. If the demo works, it works because discovery worked.
